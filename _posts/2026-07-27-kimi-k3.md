Last week, [we previewed](https://vllm.ai/blog/2026-07-22-kimi-k3-preview) the production-scale integration work for Kimi K3. Today Moonshot AI's weights are public and the support is live: we're thrilled to announce **day-0 vLLM support for Kimi K3**, one of the most powerful open-weight models ever released.

![Figure 1: Kimi K3 × vLLM — day-0 support.](/assets/figures/kimi-k3/hero-kimi-k3-vllm.webp)

Kimi K3 is a 2.8-trillion-parameter Mixture-of-Experts model (16 of 896 experts active per token) built on **Kimi Delta Attention (KDA)** and **Attention Residuals (AttnRes)**, with a 1M-token context window and native vision. The hard part is not loading it. It is making KDA, MXFP4 MoE execution, KV-cache management, prefill/decode disaggregation, speculative decoding, and long-context deployment recipes work together in a serving engine you can actually run.

The [preview post](https://vllm.ai/blog/2026-07-22-kimi-k3-preview) explained the kernel and cache architecture — in particular the challenge of **prefix caching that works on recurrent state**. This release post is the practical guide: how vLLM adapts to K3's architecture, the kernel work behind the numbers, what K3 is ready for on day 0, and the [recipes to run it](#deployment).

## TL;DR

- **Model:** `moonshotai/Kimi-K3` — 2.8T parameters; 896 experts, each token routed to the 16 most relevant; 4-bit (MXFP4) weights.
- **Speculator:** a DSpark draft model, trained and open-sourced by the Inferact team.
- **Hardware:** NVIDIA B200, B300, GB200, GB300; plus AMD ROCm support.
- **Modality:** text and native vision in, text out.
- **Context:** up to 1,000,000 tokens.
- **New in vLLM core:** prefix caching over recurrent (KDA) state — infrastructure that now benefits every hybrid model after K3.
- **Features:** tool calling, reasoning output, and structured output — all live at launch.
- **Performance (8× GB300):** ~100 tok/s single-stream; **155 tok/s with DSpark (2.1×) on reasoning workloads**; ~1,420 tok/s at 64 concurrent users (1k-token prompts → 512-token outputs). _(Numbers provisional — see [Performance](#performance).)_
- **Ready for production** across three axes: **ultra-low latency** (DSpark speculative decoding), **large-scale serving** (PD disaggregation), and **agentic serving** (Mooncake KV caching).

## Kimi K3's architecture, and how vLLM serves it

Kimi K3 departs from a standard transformer in four ways, and each one changes what a serving engine has to do. The [preview post](https://vllm.ai/blog/2026-07-22-kimi-k3-preview) covers the internals in depth; here we recap what's new and focus on **how vLLM adapts to serve it**.

### Kimi Delta Attention: a hybrid recurrent + full-attention stack

**What's new.** Most of K3's layers are KDA — a linear-attention mechanism that keeps a fixed-size recurrent *state* instead of a growing KV cache — interleaved with periodic full-attention layers that preserve exact global recall. That is what makes a 1M-token context affordable.

**How vLLM serves it.** A single **hybrid KV-cache manager** holds two kinds of memory side by side under one scheduler: paged KV blocks for the full-attention layers, and compact recurrent-state blocks for the KDA layers. A dedicated KDA attention backend runs FlashKDA for prefill and a fused CUDA kernel (or the FLA/Triton path under speculation) for decode. The hardest part is **prefix caching over recurrent state**: a KDA layer has no per-token KV to hash, so vLLM separates the *physical* KDA state-block size from the *prefix-match* granularity and reuses state snapshots at block boundaries — so long shared prompts still hit cache. This hybrid-cache machinery is [new in vLLM core](https://vllm.ai/blog/2026-07-22-kimi-k3-preview) and now benefits every hybrid model that follows K3.

![Figure 2: Kimi K3 interleaves Kimi Delta Attention (linear) layers with periodic full-attention layers; vLLM's hybrid cache manages recurrent state and paged KV together. (Draft schematic — final art TBD.)](/assets/figures/kimi-k3/kda-hybrid-layer-stack.svg)

### Attention Residuals: information flow across depth

**What's new.** AttnRes adds residual connections that carry attention information across the depth of the network, rather than only within a layer.

**How vLLM serves it.** vLLM implements AttnRes as fused Triton kernels that combine the residual add with the output RMSNorm, and shards the extra cross-layer traffic sequence-parallel so it doesn't dominate multi-GPU communication. The result is roughly **+15% TP8 prefill end-to-end** versus an unfused path (details in [Kernel optimizations](#kernel-and-serving-optimizations)).

### Stable LatentMoE: 16 of 896 experts

**What's new.** Each token is routed to 16 of 896 experts through the Stable LatentMoE framework — a very large, very sparse expert pool.

**How vLLM serves it.** Experts are sharded with **expert parallelism** and scaled with **data parallelism**. vLLM offers two MoE backends tuned for different topologies — TRT-LLM-Gen for tensor-parallel (TP>1) and MegaMoE for disaggregated/expert-parallel (DEP) — and **Expert-Parallel Load Balancing (EPLB)** to keep a few hot experts from stalling a shard. The weights execute natively in MXFP4 on the MoE path.

![Figure 3: The 2.8T, 16-of-896 MoE is served with expert and data parallelism; EPLB smooths routing skew, and MegaMoE / TRT-LLM-Gen back the two topology paths. (Draft schematic — final art TBD.)](/assets/figures/kimi-k3/moe-2p8t-ep-dp.svg)

### MXFP4 weights and native vision

**What's new.** K3's weights are quantization-aware trained in 4-bit **MXFP4**, and it is natively multimodal (image + text in).

**How vLLM serves it.** The MoE runs through an MXFP4 execution path (NVIDIA on Blackwell; AMD via FlyDSL A16W4/A8W4), and a multimodal preprocessing path turns image inputs into patch tensors alongside text. One clarification worth keeping: **MXFP4 describes the weights and MoE math, not the KV cache** — KV-cache dtype is a separate serving decision.

### Serving semantics: a render program, not a Jinja template

K3 ships **without a Jinja chat template** — its tokenizer renders messages through a *program* instead. That lets the renderer tokenize eagerly so structural markers keep their special-token ids while user- and tool-supplied text stays ordinary tokens. vLLM implements the same render program in both the Python and Rust frontends, so tool calling, reasoning output, and structured output behave identically across both.

## Built for production

Serving a 2.8T hybrid MoE well means being fast for one user, efficient for thousands, and sticky for agents. vLLM ships Kimi K3 ready on all three.

### Ultra-low latency: speculative decoding with DSpark

At 2.8T parameters, latency-sensitive serving — one user or a handful of concurrent streams — is **bandwidth-bound**: every step streams the active weights through the GPUs no matter how few tokens come out. The fix is **speculative decoding**: a compact draft model proposes a block of tokens, and K3 checks them all at once.

**DSpark** is the strongest form of that idea for K3 — it drafts the whole block in one parallel pass and keeps it coherent 7–8 tokens deep. Verifying N proposed tokens is *one* parallel pass through the big model — roughly the cost of generating a single token — so every token the draft got right comes along nearly free, and wrong guesses cost only that one check. The target model still decides every token, so quality doesn't degrade — and we checked anyway: GSM8K scores **0.968 with DSpark, 0.964 without**.

Measured with the same build, prompt, and method: **~80 → 155 tok/s single-stream, ~2.1× on reasoning workloads.** The gain depends on how predictable the output is for the draft: math and reasoning draft best; code-heavy contexts measure ~1.4–1.8×; and at high sampling temperatures the draft's acceptance rate drops, shrinking the gain. The draft model is still improving, so ~2× is what we measured on reasoning at standard settings, not a universal constant.

Both the [draft model](https://huggingface.co/Inferact/MKE-DSpark) and the inference support are **open source as of this release**. See [Deployment](#deployment) to enable it.

![Figure 4: A lightweight DSpark draft proposes candidate tokens that Kimi K3 verifies in a single parallel pass, accelerating single-stream decode. (Draft schematic — final art TBD.)](/assets/figures/kimi-k3/dspark-mtp-specdecode.svg)

### Large-scale serving: prefill/decode disaggregation

For high-throughput fleets, vLLM serves K3 with expert and data parallelism across nodes, and with **prefill/decode (PD) disaggregation** — running prefill-heavy and decode-heavy work on separate replicas so each is sized for its own bottleneck. The validated topology routes **TP8 prefill → DP16/EP16 decode**, with KV/state moved between stages over **NIXL**.

PD disaggregation is unforgiving for a hybrid model: the recurrent KDA state, the full-attention paged KV, and the block tables all have to arrive intact. After targeted transport fixes (recycled-block zeroing, cross-node lease timing, and receive-visibility handling), the disaggregated path recovers full accuracy parity — **GSM8K 0.9682 / GPQA-Diamond 0.9192** — with no garbage output. Final hardening is landing now (see [Roadmap](#roadmap)).

### Agentic serving: Mooncake KV caching

Agentic workloads — long multi-turn sessions, tool loops, and large shared system prompts — live or die on **KV reuse**. vLLM's **Mooncake** integration lets K3 offload and reuse KV across turns and requests, so a repeated codebase, document, or agent scratchpad doesn't pay full prefill every turn. Combined with K3's prefix caching over recurrent state, this keeps long agent sessions responsive as context accumulates.

## Kernel and serving optimizations

Day-0 support that people can actually run took a stack of kernel and system work, contributed across **Inferact**, **NVIDIA**, and **Moonshot AI**. A note on reading the numbers: kernel-level (microbenchmark) speedups are labeled as such and do not translate one-to-one into end-to-end serving gains — where we have a controlled end-to-end measurement, we say so.

- **Fused MLA pre-attention and cache epilogues** *(Inferact)* — a self-contained K3 MLA layer that fuses q/kv RMSNorm with BF16/FP8 cache-insert epilogues, replacing fragile `torch.compile` dependencies with explicit kernels.
- **Attention-Residual kernels** *(Moonshot algorithm, Inferact implementation; NVIDIA large-batch variant)* — a two-kernel Triton path fusing the residual add with output RMSNorm. ~1.5–5.7× at the kernel level and about **+15% TP8 prefill end-to-end**.
- **KDA decode** *(NVIDIA fused CUDA for the standard path; FLA/Triton for speculation)* — standard non-speculative decode uses NVIDIA's fused CUDA KDA kernel (conv + sigmoid + RMSNorm fused); the DSpark/MTP path uses the Inferact-integrated FLA/Triton kernels, which compose correctly with speculative state.
- **KDA metadata path** *(Inferact)* — cutting per-step host/metadata work from **~870 µs to ~34 µs** (graph staging, a custom Triton gather, and PDL), for a controlled **+5.7–6.7% end-to-end** DSpark gain.
- **MoE execution** *(NVIDIA TRT-LLM-Gen for TP>1; Inferact MegaMoE for DEP)* — for TP>1, NVIDIA's TRT-LLM-Gen MoE with grouped Top-K (up to ~4.5× kernel) and model-shape routing (~1.37–1.71× kernel); for disaggregated / expert-parallel topologies, Inferact's MegaMoE with TP/EP sequence parallelism. Shared-expert up-projection is overlapped/fused to hide communication.
- **Decode GEMM shape selection** *(Inferact)* — an SM103 shape-based selector and fused-A path, **+12% end-to-end** in a controlled B300 TP8, no-DSpark run.
- **Communication** *(FlashInfer)* — `mnnvl` one-sided all-reduce on Blackwell multi-node deployments trims tensor-parallel overhead.

## Deployment

### Quick start

```shell
vllm serve moonshotai/Kimi-K3 \
  --tensor-parallel-size 8 \
  --trust-remote-code \
  --load-format fastsafetensors \
  --enable-prefix-caching \
  --max-num-seqs 512 --max-model-len 32768 \
  --enable-auto-tool-choice --tool-call-parser kimi_k3 \
  --reasoning-parser kimi_k3
```

The exact recipe depends on the accelerator, KV dtype, context length, traffic shape, and whether the deployment prioritizes throughput, latency, or maximum context capacity. The 2.8T MoE requires at least one 8× B300 node to run at all, and most production deployments run multi-node, connected with RDMA or NVLink. Full recipes — including multi-node, expert-parallel, and vision configurations — are in the [Kimi-K3 recipes](https://recipes.vllm.ai/moonshotai/Kimi-K3).

### Enable DSpark speculative decoding

```shell
export VLLM_USE_BREAKABLE_CUDAGRAPH=0
export VLLM_USE_NCCL_SYMM_MEM=0
# then add to the serve command:
  --speculative-config '{"model":"Inferact/Kimi-K3-DSpark","method":"dspark","num_speculative_tokens":7}'
```

### Reproduce our benchmark

```shell
export NCCL_DMABUF_ENABLE=0 VLLM_USE_NCCL_SYMM_MEM=0 NCCL_CUMEM_ENABLE=1 NCCL_MNNVL_ENABLE=1 NCCL_NVLS_ENABLE=1
export VLLM_FLASHINFER_ALLREDUCE_BACKEND=mnnvl VLLM_ALLREDUCE_USE_FLASHINFER=1
export VLLM_ENGINE_READY_TIMEOUT_S=3600
export VLLM_USE_BREAKABLE_CUDAGRAPH=0

vllm serve moonshotai/Kimi-K3 --enable-prefix-caching \
  --tensor-parallel-size 8 --nnodes 2 --node-rank 0 \
  --moe-backend auto --trust-remote-code --load-format fastsafetensors \
  --max-num-seqs 512 --gpu-memory-utilization 0.9 --max-model-len 32768 \
  --speculative-config '{"model":"Inferact/Kimi-K3-DSpark","num_speculative_tokens":7,"method":"dspark"}'
```

### Deployment notes, each from a real incident

1. **`--enable-prefix-caching` turns prefix caching on**, which is *not* on by default for K3. vLLM configures the rest of the hybrid cache for you: paged KV blocks for the full-attention layers, snapshot-based reuse for the recurrent ones. ([The preview post](https://vllm.ai/blog/2026-07-22-kimi-k3-preview) explains how the two are kept in step.)
2. **Tool calling: validate on your own traffic before depending on it.** We've occasionally seen K3 emit a tool-call format its own parser doesn't expect, yielding an empty `tool_calls` — while clean probes on the same setup parse perfectly. It's prompt- and run-dependent, not a blanket failure, but production agents should validate against your schema, retry or fall back when `tool_calls` comes back empty, and consider strict/structured tool calling, which constrains the output grammar during generation.
3. **`--all2all-backend`** decides how the MoE experts communicate during expert parallelism. Use `flashinfer_nvlink_one_sided` for NVLink and `deepep_v2` for RDMA.
4. **`--moe-backend`** — vLLM has several MoE backends for different scenarios. We recommend `deep_gemm_mega_moe` for any DEP environment and `flashinfer_trtllm` for TP>1.
5. **`VLLM_USE_V2_MODEL_RUNNER=1` and `VLLM_USE_RUST_FRONTEND=1`** — Model Runner v2 and the Rust frontend fully support this model and can be enabled if needed.

## Kimi K3 vLLM FAQ

### Does vLLM support Kimi K3?

Yes — day-0 support for `moonshotai/Kimi-K3`, including KDA hybrid attention, MXFP4 MoE execution, the `kimi_k3` tool and reasoning parsers, native vision, DSpark speculative decoding, and TP/EP/DP serving recipes.

### How many GPUs do I need to serve Kimi K3?

At least one 8× B300 (or GB300) node to run at all; most production deployments run multi-node with expert and data parallelism, connected over RDMA or NVLink.

### How do I enable DSpark speculative decoding?

Add `--speculative-config '{"model":"Inferact/Kimi-K3-DSpark","method":"dspark","num_speculative_tokens":7}'` and set `VLLM_USE_BREAKABLE_CUDAGRAPH=0`. It roughly doubles single-stream decode on reasoning workloads; the gain is smaller on code and at high temperature.

### Which MoE backend should I use?

`deep_gemm_mega_moe` for disaggregated / expert-parallel (DEP) deployments, and `flashinfer_trtllm` for TP>1. Pick the all-to-all backend to match your interconnect: `flashinfer_nvlink_one_sided` for NVLink, `deepep_v2` for RDMA.

### Does Kimi K3 support prefix caching, and is it on by default?

It supports prefix caching over both full-attention KV and recurrent KDA state, but it is **not on by default** — pass `--enable-prefix-caching`.

### Does vLLM support Kimi K3 on AMD GPUs?

Yes — ROCm support ships at launch, with broader tuning on the roadmap.

### How is this different from the Kimi K3 preview post?

The [preview](https://vllm.ai/blog/2026-07-22-kimi-k3-preview) is the architecture and kernel deep dive (how KDA prefix caching and the kernels are built). This post is the practical launch guide: how vLLM adapts to K3, recipes, flags, performance, and what K3 is ready for in production.
