We are excited to announce day-0 vLLM support for Kimi K3, Moonshot AI's new flagship model, including the MXFP4 and BF16 checkpoints at [`moonshotai/Kimi-K3`](https://huggingface.co/moonshotai/Kimi-K3) and the multi-token-prediction draft at [`moonshotai/Kimi-K3-MTP`](https://huggingface.co/moonshotai/Kimi-K3-MTP).

Kimi K3 is a 2.8-trillion-parameter Mixture-of-Experts model (16 of 896 experts active per token) built on the KimiLinear hybrid attention stack, with a 1M-token context window and native vision. The hard part is not loading it. It is making Kimi Delta Attention, MXFP4 MoE execution, prefill/decode disaggregation, speculative decoding, and long-context deployment recipes work together in a serving engine you can actually run.

We covered the kernel and cache internals — including the hardest problem, prefix caching over KDA state — in our [pre-release deep dive](https://vllm.ai/blog/2026-07-22-kimi-k3-preview). This post is the practical launch companion: how to run Kimi K3 on vLLM, which knobs matter, and what it delivers on day 0.

![Figure 1: Kimi K3 × vLLM — iron-filing magnetic field lines in vLLM gold and blue converging on the vLLM logo, marking day-0 support for Kimi K3.](/assets/figures/kimi-k3/hero-kimi-k3-vllm.webp)

## TL;DR

vLLM ships initial day-0 support for Kimi K3:

- **Model family:** MXFP4 and BF16 Kimi K3 checkpoints plus the `Kimi-K3-MTP` speculative-decoding draft, with 1M-token (1,048,576) context subject to hardware capacity and deployment configuration.
- **Core architecture:** KimiLinear — mostly Kimi Delta Attention (KDA, a hybrid linear attention) with periodic full-attention layers, Attention Residuals, Stable LatentMoE routing (16 of 896 experts), SiTU activation, and Gated MLA. See the [deep dive](https://vllm.ai/blog/2026-07-22-kimi-k3-preview) for the kernels behind each.
- **Serving stack:** OpenAI-compatible API with always-on reasoning (`reasoning_effort`), tool calling, structured output, and base64 vision; `kimi_k3` tool and reasoning parsers; TP/EP/DP deployment; prefix caching; prefill/decode disaggregation; and DSpark speculative decoding.
- **Performance work:** MXFP4 MoE via DeepGEMM and MegaMoE backends, Expert-Parallel Load Balancing (EPLB), FlashKDA and fused KDA decode, FlashInfer `mnnvl` all-reduce, and a DSpark decode path that roughly doubles single-stream throughput. NVIDIA (Blackwell) and AMD (FlyDSL A16W4/A8W4) paths.
- **Roadmap:** deeper CUDA-graph coverage, broader disaggregated-serving recipes, and continued MoE and long-context tuning after day 0.

## Quickstart: Run Kimi K3 with vLLM

The MXFP4 checkpoint is the recommended starting point on a Blackwell-class node:

```bash
vllm serve moonshotai/Kimi-K3 \
  --trust-remote-code \
  --tensor-parallel-size 8 \
  --enable-expert-parallel \
  --moe-backend deep_gemm_mega_moe \
  --enable-prefix-caching \
  --max-model-len 1048576 \
  --tool-call-parser kimi_k3 \
  --reasoning-parser kimi_k3
```

For the BF16 checkpoint:

```bash
vllm serve moonshotai/Kimi-K3 \
  --trust-remote-code \
  --tensor-parallel-size 8 \
  --enable-expert-parallel \
  --moe-backend auto \
  --enable-prefix-caching \
  --max-model-len 1048576 \
  --tool-call-parser kimi_k3 \
  --reasoning-parser kimi_k3
```

The exact recipe depends on the accelerator, model dtype, context length, traffic shape, and whether the deployment prioritizes throughput, latency, or maximum context capacity. The 2.8T MoE is large enough that most production deployments run multi-node with expert and data parallelism; the day-0 path is validated on a 16-GPU DP16 + EP16 topology on Blackwell (B200/B300/GB300), with both x86 and ARM images.

### Deployment Knobs That Matter

Kimi K3 has a few knobs that matter more than usual.

- **`--moe-backend`** selects the expert execution path. `auto` uses vLLM's fused MoE with the LatentMoE runner; `deep_gemm_mega_moe` (paired with `--enable-expert-parallel`) routes through the MegaMoE path, which is the throughput-oriented choice for large expert-parallel deployments.
- **`--enable-expert-parallel`** shards the 896 experts across GPUs. Combine it with data parallelism to scale request throughput once experts fit.
- **`--enable-eplb`** turns on Expert-Parallel Load Balancing so a few hot experts don't stall an entire shard. Under real traffic this raised routing balance from ~0.93 to ~0.99 in our validation.
- **`--max-model-len`** sets the advertised context and drives KV/state cache planning. KDA's linear layers keep per-token state bounded, but the periodic full-attention layers still need paged KV, so long-context capacity is a real planning input.
- **`--enable-prefix-caching`** matters because Kimi K3 workloads reuse long prompts (codebases, documents, multi-turn agent traces). vLLM's KDA prefix caching separates the physical KDA state-block size from prefix-match granularity so long shared prefixes still hit cache — the mechanism is described in the [deep dive](https://vllm.ai/blog/2026-07-22-kimi-k3-preview).
- **Tool and reasoning parsers** (`kimi_k3`) should be enabled for agent workloads so tool calls and reasoning traces come back as structured fields.

![Figure 2: Kimi K3 interleaves Kimi Delta Attention (linear) layers with periodic full-attention layers to keep a 1M-token context practical to serve.](/assets/figures/kimi-k3/kda-hybrid-layer-stack.svg)

### Speculative Decoding with DSpark (MTP)

Kimi K3 ships a multi-token-prediction (MTP) draft, `Kimi-K3-MTP`, that pairs with vLLM's DSpark speculative decoding to accelerate decode. The draft proposes several candidate tokens each step and the full model verifies them in a single pass:

```bash
export VLLM_USE_BREAKABLE_CUDAGRAPH=0   # required for DSpark graph-mode capture

vllm serve moonshotai/Kimi-K3 \
  --trust-remote-code \
  --tensor-parallel-size 8 \
  --enable-expert-parallel \
  --moe-backend deep_gemm_mega_moe \
  --enable-prefix-caching \
  --max-model-len 1048576 \
  --tool-call-parser kimi_k3 \
  --reasoning-parser kimi_k3 \
  --speculative-config '{"model": "moonshotai/Kimi-K3-MTP", "num_speculative_tokens": 7, "method": "dspark"}'
```

> [!TIP]
> Start from this recipe, confirm accuracy on your workload, then tune `num_speculative_tokens` and the EP/DP split for your traffic. DSpark helps most for latency-sensitive, single-stream and low-batch decode.

![Figure 3: A lightweight MTP draft proposes candidate tokens that Kimi K3 verifies in parallel, roughly doubling single-stream decode throughput in engineering validation.](/assets/figures/kimi-k3/dspark-mtp-specdecode.svg)

### Reasoning, Tools, and Vision

Kimi K3 exposes an OpenAI-compatible surface. Reasoning is always on; you control the effort level, and the reasoning trace streams back separately from the final answer:

```python
from openai import OpenAI

client = OpenAI(api_key="EMPTY", base_url="http://localhost:8000/v1")
model = client.models.list().data[0].id

# Reasoning effort + separate reasoning_content stream
stream = client.chat.completions.create(
    model=model,
    messages=[{"role": "user", "content": "Prove that sqrt(2) is irrational."}],
    extra_body={"reasoning_effort": "high"},  # low | high | max (default: max)
    max_completion_tokens=8192,
    stream=True,
)
for chunk in stream:
    delta = chunk.choices[0].delta
    if getattr(delta, "reasoning_content", None):
        print(delta.reasoning_content, end="")   # the thinking trace
    if delta.content:
        print(delta.content, end="")             # the final answer
```

Tool calling (including forced tool use) and strict structured output work through the same API:

```python
response = client.chat.completions.create(
    model=model,
    messages=[{"role": "user", "content": "What is the weather in Beijing?"}],
    tools=[{
        "type": "function",
        "function": {
            "name": "get_weather",
            "parameters": {"type": "object", "properties": {"city": {"type": "string"}}},
        },
    }],
    tool_choice="required",
)
print(response.choices[0].message.tool_calls)
```

Vision inputs are passed as base64 image URLs in the standard multimodal message format; the `--max-model-len` budget is shared across text and image tokens.

## Model Key Features for Serving

Kimi K3 matters for inference systems in a few directions.

### 1M-Token Context with Kimi Delta Attention

The central architectural change is KimiLinear: most layers use Kimi Delta Attention, a hybrid linear attention that keeps per-token state bounded instead of growing linearly with sequence length, while periodic full-attention layers preserve exact global recall. Together they make a 1,048,576-token context tractable to serve. The kernel and prefix-cache internals live in the [deep dive](https://vllm.ai/blog/2026-07-22-kimi-k3-preview); what matters for deployment is that long, reused prompts stay cheap.

### 2.8T-Parameter MoE with Stable LatentMoE

Kimi K3 routes each token to 16 of 896 experts through the Stable LatentMoE framework, reported at roughly 2.5× the scaling efficiency of Kimi K2. For serving, this means expert parallelism is the primary scaling lever, and expert load balancing (EPLB) is worth enabling so routing skew under real traffic doesn't bottleneck a single shard.

![Figure 4: Stable LatentMoE routes each token to 16 experts; vLLM shards the 896 experts with expert and data parallelism, with EPLB smoothing routing skew.](/assets/figures/kimi-k3/moe-2p8t-ep-dp.svg)

### MXFP4 Weights and MXFP8 Activations

Kimi K3 is trained quantization-aware with MXFP4 weights and MXFP8 activations, so low precision is native rather than a post-hoc conversion. vLLM executes the MoE through an MXFP4 path on NVIDIA Blackwell and through FlyDSL A16W4/A8W4 operators on AMD.

> [!IMPORTANT]
> MXFP4 describes the model weight and MoE execution path. It does not mean the KV cache is quantized — KV-cache dtype is a separate serving decision. Public recipes should state model dtype, MoE backend, and KV-cache policy independently.

### Native Vision

Kimi K3 is multimodal: the serving path preprocesses image and video inputs into patch tensors and runs them through the same OpenAI-compatible surface as text, tool, and reasoning traffic. As with any multimodal deployment, keeping CPU-heavy media decode and resizing upstream of the GPU worker keeps generation scheduling predictable.

## vLLM Implementation

> [!NOTE]
> This section describes how Kimi K3's architecture surfaces as serving behavior and flags. For the kernel-level details — FlashKDA, fused KDA decode, Attention Residuals kernels, the reimplemented MLA module, and MXFP4-with-SiTU internals — see the [pre-release deep dive](https://vllm.ai/blog/2026-07-22-kimi-k3-preview). If you are new to vLLM internals, [Anatomy of vLLM](https://vllm.ai/blog/2025-09-05-anatomy-of-vllm) is a good companion.

### KDA Attention Backend and the Hybrid Layer Layout

Kimi K3 is a hybrid model: most layers route to the KDA linear-attention backend, while periodic layers route to standard full attention. vLLM keeps that distinction behind the model and attention backend, so the scheduler, cache allocation, batching, and prefix caching continue to look familiar. For prefix caching, vLLM separates the physical KDA state-block size from the prefix-match granularity, so long shared prompts still produce useful cache hits without storing recurrent state at every small block.

### MoE Execution: EP/DP and the MXFP4 Path

The 896-expert MoE is sharded with expert parallelism and scaled with data parallelism. `--moe-backend auto` uses the fused MoE with the LatentMoE runner; `deep_gemm_mega_moe` routes through the MegaMoE path for large expert-parallel deployments. Both consume the MXFP4-packed expert weights. The day-0 configuration is validated on a DP16 + EP16 topology.

### Prefill, Decode, and Prefill/Decode Disaggregation

A reimplemented MLA module gives Kimi K3 clean prefill and decode code paths and enables prefill/decode (PD) disaggregation, so prefill-heavy and decode-heavy work can be placed on separate replicas. This builds on the directions in [Large-Scale Serving with vLLM](https://vllm.ai/blog/2025-12-17-large-scale-serving).

### Parser and API Integration

Kimi K3 uses model-specific parsers so agent traffic comes back structured: `--reasoning-parser kimi_k3` extracts the reasoning trace into `reasoning_content`, `--tool-call-parser kimi_k3` turns tool-call conventions into structured `tool_calls`, and strict `json_schema` structured output is supported through the standard API.

## Performance

Kimi K3 shifts where time goes, and the day-0 implementation focuses on keeping the new pieces cheap:

- **DSpark speculative decoding** accelerates decode by verifying MTP-proposed tokens in one pass; the speedup is workload-dependent (higher on real traffic where the draft's proposals are accepted).
- **MegaMoE / DeepGEMM MXFP4 kernels** keep the 16-of-896 expert path efficient under expert parallelism.
- **EPLB** smooths routing skew so throughput is not capped by the busiest expert shard.
- **FlashKDA and fused KDA decode** keep the linear-attention path off the critical decode budget.
- **FlashInfer `mnnvl` all-reduce** reduces tensor-parallel communication overhead on Blackwell multi-node deployments.
- **AMD FlyDSL** A16W4/A8W4 quantized operators bring the MXFP4 MoE path to ROCm.

## Kimi K3 vLLM FAQ

### Does vLLM support Kimi K3?

Yes. vLLM ships day-0 support for the Kimi K3 MXFP4 and BF16 checkpoints, including KDA hybrid attention, MXFP4 MoE execution, the `kimi_k3` tool and reasoning parsers, native vision, DSpark speculative decoding, and TP/EP/DP serving recipes.

### How do I run Kimi K3 with vLLM?

Use `vllm serve moonshotai/Kimi-K3` with `--trust-remote-code`, `--enable-expert-parallel`, `--enable-prefix-caching`, a `--max-model-len` target, and the `kimi_k3` parsers. See the [Quickstart](#quickstart-run-kimi-k3-with-vllm) above for full commands.

### How many GPUs do I need to serve Kimi K3?

Kimi K3 is a 2.8T-parameter MoE, so it is a multi-node deployment for most users. The day-0 path is validated on a 16-GPU DP16 + EP16 Blackwell topology; scale expert and data parallelism to your context length and traffic.

### What is Kimi Delta Attention (KDA) and why does it matter for serving?

KDA is a hybrid linear attention: most layers keep per-token state bounded (cheap long context), while periodic full-attention layers preserve exact global recall. It is what makes Kimi K3's 1M-token context practical to serve. The kernel and cache internals are in the [deep dive](https://vllm.ai/blog/2026-07-22-kimi-k3-preview).

### What context length does Kimi K3 support on vLLM, and how do I enable it?

Kimi K3 supports up to 1,048,576 tokens, subject to hardware capacity and deployment configuration. Set `--max-model-len 1048576` (or a smaller target that fits your KV/state budget) and enable prefix caching.

### Does MXFP4 mean the KV cache is also quantized?

No. MXFP4 describes the model weights and MoE execution path. KV-cache dtype is a separate serving decision; state model dtype, MoE backend, and KV-cache policy independently in your recipe.

### How do I enable DSpark speculative decoding for Kimi K3?

Pass `--speculative-config '{"model": "moonshotai/Kimi-K3-MTP", "num_speculative_tokens": 7, "method": "dspark"}'` and set `VLLM_USE_BREAKABLE_CUDAGRAPH=0` for graph-mode capture. In single-stream validation this roughly doubled decode throughput.

### Which MoE backend should I use — `auto` or `deep_gemm_mega_moe`?

`auto` uses vLLM's fused MoE with the LatentMoE runner and is a good default. `deep_gemm_mega_moe` with `--enable-expert-parallel` routes through the MegaMoE path and is the throughput-oriented choice for large expert-parallel deployments.

### How do I control reasoning effort and get reasoning output?

Reasoning is always on. Set `reasoning_effort` to `low`, `high`, or `max` (default `max`) via `extra_body`, and read the streamed `reasoning_content` deltas separately from the final `content`. Enable `--reasoning-parser kimi_k3`.

### How do I use tool calling and structured output with Kimi K3?

Enable `--tool-call-parser kimi_k3`, pass `tools` in the request, and optionally `tool_choice="required"` to force a tool call. Strict `json_schema` structured output is supported through the standard OpenAI-compatible API.

### How do I send images or video to Kimi K3 on vLLM?

Kimi K3 is natively multimodal. Send base64 image URLs in the standard multimodal message format; image and text tokens share the `--max-model-len` budget. Keep CPU-heavy media decoding upstream of the GPU worker.

### Does vLLM support Kimi K3 on AMD GPUs?

Yes. The MXFP4 MoE path is implemented on AMD via FlyDSL A16W4/A8W4 quantized operators, alongside the NVIDIA Blackwell path.
